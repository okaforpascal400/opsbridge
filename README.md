# OpsBridge

Demo video: coming soon.
<!-- demo video link goes here once it is recorded (Phase 7) -->

OpsBridge is an AI agent for a fragmented B2B operations stack: a legacy Postgres
table, a spreadsheet export, PDFs and an undocumented partner API. It answers
natural-language operations questions across all of them and proposes write-actions
that a human confirms before anything commits.

Phases 1 to 5 are built: the messy legacy world, the schema adapter that reconciles it, a
read-only tool-calling agent with an MCP server, the guardrail write path behind a human
confirmation, and tracing with an eval suite over all of it. Guardrail hardening continues
and the packaging work is Phase 7. See ROADMAP.md for the phase status.

## Evals

The system is measured, not just run. Two tiers:

| Suite | Cases | What it proves | When it runs |
| --- | --- | --- | --- |
| `evals/run.py`, deterministic | 15 | pipeline counts, matcher tiers, guardrail policy | CI, every push and pull request |
| `evals/live.py`, live agent | 4 | the agent picks the right tools and answers correctly against real Claude | on demand, needs an API key |

The deterministic suite covers pipeline counts, matcher tiers, and the guardrail policy
(confirm-by-status and the refund safety rules). It calls no model, so it is free and
reproducible, and it exits non-zero on a failed case, which fails the build.

## The seeded mess

The fixture data is generated by `legacy/seed_data.py` and loaded by
`legacy/seed_db.py`. It is deterministic: same seed, same 200 orders and same 40
returns, every run, on every machine. Every messy variant is guaranteed present by
construction rather than by a lucky draw, so tests can assert on structure.

### legacy.orders

200 rows. Six of the seven columns are text, on purpose.

| Column | Type | What is wrong with it |
| --- | --- | --- |
| `order_id` | `INTEGER PRIMARY KEY` | Clean. 1 to 200. The only clean column here. |
| `cust_name` | `TEXT NULL` | One of two half-migrated columns for the same fact. About 85 percent of rows use this one. |
| `customer` | `TEXT NULL` | The other one. Exactly one of the two is populated per row, never both, never neither. |
| `order_date` | `TEXT NOT NULL` | Three formats mixed across rows: `2026-06-15`, `07/03/2026` and `February 13, 2026`. The slashed form is genuinely ambiguous between day/month and month/day. Dates span 2026-01-01 to 2026-06-30. |
| `status` | `TEXT NOT NULL` | Free text typed by whoever was on the phone: `confirmed`, `CONF`, `pending call`, `PENDING`, `delivered`, `returned?`, and the empty string. |
| `phone` | `TEXT NOT NULL` | The same Nigerian mobile number written three ways: `+2348063900527`, `08063900527`, `8063900527`. |
| `amount` | `TEXT NOT NULL` | Two shapes sharing one column: `N162,500` and `54550`. A typed column could not hold both, which is exactly why the source system used text. |

### data/returns.csv

40 rows, written by the seed. Header: `customer_name,phone,amount,reason`.

There is no `order_id` column. Name plus phone is the only path back to an order, and
both were re-keyed somewhere upstream, so neither matches exactly. Names are varied
deliberately: a middle name dropped, two adjacent letters in the surname transposed, a
trailing vowel dropped, a letter doubled, and a minority left alone. Each phone is
written in a different one of the three formats than its order uses, so a raw string
join returns nothing. Amounts are text in both shapes and often smaller than the order
value, because partial refunds are normal.

### The partner delivery API

`legacy/partner_api.py` is a second FastAPI app standing in for an external delivery
service. It answers in XML, not JSON. It keys deliveries on its own private phone
convention (strip non-digits, keep the last 10) that nobody wrote down. Its delivery
states (`IN_TRANSIT`, `DELIVERED`, `AT_HUB`, `FAILED_ATTEMPT`, `RETURNED`) do not line
up with the free-text statuses in the orders table. An unknown phone number gets HTTP
200 with state `UNKNOWN` rather than a 404, which is the kind of undocumented behaviour
that lets a naive client store a delivery state that means nothing.

None of this is an oversight, and a reviewer should not tidy it up. It is the seam the
schema adapter closes: `schema_adapter/` reconciles the orders table and the returns export
into one canonical model. The partner API's quirks are not handled yet, since the tool that
reads it is deferred with the RAG work, so that part of the mess is still waiting. The seed
tests fail if the mess goes away.

## Running it locally

Requires Python 3.14 and Docker.

1. Create the virtualenv and install dependencies.

   ```
   python -m venv .venv
   ```

   Activate it. PowerShell:

   ```
   .venv\Scripts\Activate.ps1
   ```

   bash:

   ```
   source .venv/bin/activate
   ```

   Then:

   ```
   pip install -r requirements.txt
   ```

2. Create your `.env`. bash:

   ```
   cp .env.example .env
   ```

   PowerShell:

   ```
   Copy-Item .env.example .env
   ```

   The database defaults match the docker compose service. `ANTHROPIC_API_KEY` is
   required to run the agent, which calls the Anthropic API. The tests stub the model and
   do not need it.

3. Start Postgres and wait for it to report healthy.

   ```
   docker compose up -d
   docker compose ps
   ```

   The `STATUS` column should read `Up (healthy)`. To check the server directly:

   ```
   docker compose exec postgres pg_isready -U opsbridge -d opsbridge
   ```

4. Create the throwaway test database. Compose only creates `opsbridge`, and the seed
   tests need their own database because seeding drops the whole `legacy` schema. Once
   per machine:

   ```
   docker compose exec postgres createdb -U opsbridge opsbridge_test
   ```

5. Seed the legacy database and write the returns export.

   ```
   python -m legacy.seed_db
   ```

   It prints one summary line and writes `data/returns.csv`. It is destructive and
   idempotent: it drops and recreates the `legacy` schema in whatever database
   `DATABASE_URL` points at, then writes the same 200 rows every time.

6. Run the OpsBridge API and hit the health endpoint.

   ```
   uvicorn api.main:app --reload --port 8000
   curl http://localhost:8000/health
   ```

   Expected body: `{"status":"ok"}`.

7. Run the partner API in a second terminal, on its own port.

   ```
   uvicorn legacy.partner_api:app --port 8100
   curl http://localhost:8100/ping
   curl "http://localhost:8100/status?phone=08063900527"
   ```

   `/ping` returns the plain text `ok`. `/status` returns an XML `<delivery>` document
   with `<phone>`, `<state>` and `<last_update>`. The same record comes back for
   `+2348063900527` and `8063900527`. A number the partner has never seen, for example
   `08000000000`, still returns 200, with state `UNKNOWN` and an empty `last_update`.

   In PowerShell, `curl` is an alias for `Invoke-WebRequest`. Use `curl.exe` for the
   commands above, or open the URLs in a browser.

## Tests

```
pytest
```

The pure fixture tests, the partner API tests and the health test run anywhere with no
database.

The database tests are gated on the `OPSBRIDGE_TEST_DATABASE_URL` environment variable and
skip with an explanatory message when it is unset: `tests/test_seed.py` (the seed round
trip), `tests/test_pipeline.py` and `tests/test_tools.py` (the pipeline and the read tools
over seeded data), and `tests/test_actions.py` (the confirm flow, which writes audit rows).
Point it at a throwaway database, never at your development one: the seed drops and
recreates the `legacy` schema, and the confirm tests empty `opsbridge.actions` between
tests. pytest reads this from the process environment, not from `.env`, so set it in the
shell you run pytest in.

PowerShell:

```
$env:OPSBRIDGE_TEST_DATABASE_URL = "postgresql+psycopg2://opsbridge:opsbridge@localhost:5432/opsbridge_test"
```

bash:

```
export OPSBRIDGE_TEST_DATABASE_URL=postgresql+psycopg2://opsbridge:opsbridge@localhost:5432/opsbridge_test
```

Lint with:

```
ruff check .
```

## Project layout

```
opsbridge/
  api/                 FastAPI app: /health, POST /confirm, GET /trace/{id}
  legacy/              the seeded mess: row generator, DB seed, partner API
  schema_adapter/      canonical models, normalizers, return-to-order matcher, pipeline
  agent/               read tools, tool schemas, tool-calling loop, and the Conversation
  mcp_server/          FastMCP stdio server exposing the read tools
  guardrails/          proposal contract, policy gate, and the confirm flow that writes
                       to the append-only opsbridge.actions table
  observability/       empty until Phase 5: trace store and the /trace endpoint
  evals/               empty until Phase 6: golden dataset, scoring harness, report
  tests/               pytest suite
  config.py            environment-specific settings, read in exactly one place
  docker-compose.yml   local Postgres 16
  pyproject.toml       ruff and pytest configuration
  ROADMAP.md           phased delivery plan
  DECISIONS.md         architecture decision log
  CLAUDE.md            working agreement for this repo
```

The empty packages (observability/ and evals/) hold a one-line docstring naming their
phase and nothing else. They stay empty until that phase starts, on purpose.

## CI

GitHub Actions runs `ruff check .` and `pytest` against a Postgres 16 service container
on every push and pull request, so the database-backed seed tests always execute in CI.
